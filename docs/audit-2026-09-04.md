## A — THE LEADERBOARD. Why autosync users are not on it properly.

**The page never calls the endpoint that was built for it.** `Leaderboard.tsx` has two tabs, and
BOTH call `/api/leaderboard/by-session` — the "Overall" tab just calls it with no session filter
(`Leaderboard.tsx:108`). `/api/leaderboard`, which does the per-user aggregation and the name
lookup, has **no caller anywhere in the client**.

That one wiring mistake causes three separate faults:

### A1 — "Overall" is not overall, and it splits an autosync trader in two
`/api/leaderboard/by-session` groups by `ts.id` — *"One row per (trading_session, user) — no
cross-session aggregation"* (`routes.ts:816`). Connecting a broker account auto-creates its own
trading session (`routes.ts:3904-3922`), and auto-journaled trades go into that session while
hand-typed trades go into his own. So one trader appears **twice on the Overall board with their
P&L split between the rows** — which is exactly the autosync case.

### A2 — a trade with no session can never appear at all
That query starts `FROM trading_sessions ts JOIN journal_entries je ON je.session_id = ts.id` — an
INNER join. `brokerSyncService.ts:130` journals under `account?.defaultSessionId ?? null`. Any
account whose default session is null (created before that code, or its session deleted) produces
journal entries that are **invisible on both tabs, permanently**.

### A3 — the name is never looked up on the endpoint the page actually uses
`backfillProfilesFromSupabase` — which fetches the name the trader **signed up with**
(`user_metadata.full_name`, set at `AuthContext.tsx:157`) — is only called from the dead
`/api/leaderboard`. On `by-session` there is no backfill, so a trader with no `user_profiles` row
shows as `Trader #A1B2` and one with a blank name shows as their **email local-part**.

### A4 — and where the backfill does exist, its filter can never fire
`routes.ts:648` selects rows to repair with `!r.full_name && !r.email` — it needs BOTH missing.
`user_profiles.email` is `NOT NULL`, so any existing profile row has an email, so a row with a
**blank name and a present email is never repaired**. That is precisely the row that shows an email
instead of a name.

### A5 — the main board ignores "hide me"
`up.leaderboard_hidden` is honoured by `by-session` (`routes.ts:817`) and **not** by
`/api/leaderboard`. An admin hiding a trader hides them from one view and not the other.

**Fix:** point "Overall" at `/api/leaderboard` (it already aggregates per user, tolerates a null
session via `LEFT JOIN` + `(je.session_id IS NULL OR ts.id IS NOT NULL)`, and carries the name
backfill); add the hidden filter to it; widen the backfill filter to `!r.full_name`; and give
`by-session` the same backfill so both tabs show signup names.

## B — OUTCOME LABELS. The same field is compared four different ways.

`journal_entries.outcome` is a free `text` column with no constraint, and **two writers use two
different casings**:

| writer | writes |
|---|---|
| the manual form (`JournalForm.tsx:774`) | `"Win"` · `"Loss"` · `"BE"` |
| the auto pipeline (`autoJournal/fields.ts` `classifyOutcome`) | `"WIN"` · `"LOSS"` · `"BE"` |
| `TradeVault` on edit (line 454) | rewrites whatever it saves to UPPERCASE |

A canonical reader already exists and already handles all of it — `classifyOutcome` in
`client/src/lib/tradeStats.ts:29`, whose own docstring calls it *"the SINGLE client-side source of
truth"*. **It is only half adopted**, and every defect below is a place that compares the raw string
instead.

### B1 — every winning trade on `/history` is displayed as a LOSS  ⚠ the worst one
`TradeHistory.tsx` compares `trade.outcome === 'win'` — **lowercase**, at lines 68, 69, 279, 377 and
383. The database holds `"Win"` or `"WIN"` and never `"win"`, so that test is **never true**:

* the card border (279) and the badge (377, 383) fall through to `destructive` — a red **LOSS**
  badge on a winning trade;
* the **Wins** and **Losses** filter buttons (68-69) match nothing and return an empty table.

And directly above it, lines 76-78 *do* use the canonical classifier — so the page prints a correct
"Win Rate 62%" over a table in which every row is labelled LOSS. `/history` is a live authed route
(`App.tsx:141`, `:278`).

### B2 — a break-even is coloured red and given a minus sign on the dashboard
`Journal.tsx:650` is `=== 'win' ? 'profit' : 'loss'`, so `BE` becomes a loss; line 753 then takes the
**sign from that class rather than from the money**, so a break-even prints `-$0.00` in red — and any
trade whose label is not exactly a win prints a minus in front of a positive number.

### B3 — the dashboard's Profit/Loss Ratio counts break-evens as losses
`Journal.tsx:656-657` divides wins by `core.totalTrades` and then sets `lossRatio = 100 -
profitRatio`. The canonical rule — stated in `metrics_calculator.py:802` and mirrored in
`tradeStats.ts:9` — excludes break-evens from **both** sides. The WIN RATE card immediately above
uses the canonical figure, so the two disagree on one screen.

### B4 — the metrics engine contradicts itself
`metrics_calculator.py` computes win rate two ways: `win_rate_of` (line 802, decisive only, correct)
for `core`, and `len(wins)/len(trades)` (line 1633, break-evens in the denominator) for the monthly
breakdown. The same trader's win rate differs between the KPI card and the monthly table.

## C — Auth

### C1 — one admin endpoint opens if `ADMIN_SECRET` is unset
`routes.ts:4247` is `if (req.query.secret !== process.env.ADMIN_SECRET)`. With the variable unset
that is `undefined !== undefined` → **false** → the request proceeds. Every other guard in the file
checks presence first; `requireAdminSecret` (line 2439) is the correct shape. Low severity —
`ADMIN_SECRET` is required and set in production — but it is a one-line gap of the exact kind the
2026-08-31 sweep was written to catch, and `?debug=1` on that route prints the cTrader client id.
